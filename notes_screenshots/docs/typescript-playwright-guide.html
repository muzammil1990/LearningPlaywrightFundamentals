1. TypeScript concepts that matter most in Playwright

  • Types and interfaces: model test data (users, API payloads) so typos fail at compile time, not at runtime.
  • async/await and Promises: every Playwright action returns a Promise. A missing await is the most common cause of flaky tests.
  • Generics: used in fixtures, API helpers, and reusable utilities (Promise<T>).
  • Classes and access modifiers: the foundation of the Page Object Model (POM).
  • Modules (import/export): organizing page objects, utils, and test data.
  • Enums and union types: environments, roles, and statuses ('admin' | 'viewer').
  • Utility types (Partial, Pick, Record): flexible test data builders.

2. Core Playwright concepts

ConceptWhat it is
Browser → Context → PageA browser has isolated contexts (like incognito profiles); each context has pages (tabs). Contexts give test isolation cheaply.
LocatorsLazy, auto-retrying references to elements. Prefer getByRole, getByLabel, getByTestId over CSS/XPath.
Auto-waitingActions wait for the element to be visible, stable, enabled, and so on. You rarely need manual waits.
Web-first assertionsawait expect(locator).toBeVisible() retries until it passes or times out.
FixturesDependency injection for tests (page, request, plus your custom ones). Replace beforeEach boilerplate.
ProjectsConfig entries to run the same tests across browsers, devices, or environments.
Trace ViewerTime-travel debugging with DOM snapshots, network, and console. Your best friend for failures.
API testingThe request fixture lets you test REST APIs and combine UI + API flows.
Network interceptionpage.route() to mock or modify responses.
Storage stateSave login once, reuse across tests (faster, more stable).

3. A small example tying it together

pages/LoginPage.ts

import { Page, Locator, expect } from '@playwright/test';

export class LoginPage {
  private readonly username: Locator;
  private readonly password: Locator;
  private readonly submit: Locator;

  constructor(private readonly page: Page) {
    this.username = page.getByLabel('Username');
    this.password = page.getByLabel('Password');
    this.submit = page.getByRole('button', { name: 'Sign in' });
  }

  async login(user: string, pass: string): Promise<void> {
    await this.username.fill(user);
    await this.password.fill(pass);
    await this.submit.click();
  }

  async expectLoggedIn(): Promise<void> {
    await expect(this.page).toHaveURL(/dashboard/);
  }
}

fixtures.ts

import { test as base } from '@playwright/test';
import { LoginPage } from './pages/LoginPage';

export const test = base.extend<{ loginPage: LoginPage }>({
  loginPage: async ({ page }, use) => {
    await use(new LoginPage(page));
  },
});
export { expect } from '@playwright/test';

tests/login.spec.ts

import { test } from '../fixtures';

test('valid user can log in', async ({ page, loginPage }) => {
  await page.goto('/login');
  await loginPage.login('demo', 'secret');
  await loginPage.expectLoggedIn();
});

4. Common points of confusion

locator vs elementHandle: use locators. Handles are legacy and don't auto-retry.
waitForTimeout: avoid it. Wait on a condition (an assertion, a response, a URL) instead.
expect with and without await: web-first assertions on locators need await; plain value assertions (expect(5).toBe(5)) don't.
test.describe.serial vs parallel: tests run in parallel by default across files, and each test gets a fresh context. Don't make tests depend on each other.
Strict mode: if a locator matches more than one element, actions throw. Narrow it with getByRole options, .filter(), or .first() only when intentional.
Page Object vs fixtures: they complement each other. POM encapsulates page behavior; fixtures wire up and share it.
